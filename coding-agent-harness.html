A Coding-Agent Architecture Study

Building a Coding Agent Harness from First Principles

Before tools, sandboxes, memory, subagents, or a terminal interface, one distinction unlocks the entire system: the language model is the reasoner inside the machine. It is not the machine.

Case study: Grok Build Level: class five doorway → production depth Built through Part VIII capstone · Part I intentionally absent

How to read this. We will not begin with Grok Build's crates. We will begin with a problem, make a prediction, and earn the first box. Only then will we open the real source and ask whether a production system follows the reasoning.

Part 0 / The First Distinction

Why a smart model still needs machinery

If this boundary is fuzzy, every later component feels arbitrary. If it is clear, tools, permissions, memory, events, and sandboxes fall out naturally.

0.1

The Model Is Not the Agent

We start here because every later word—tool, permission, state, sandbox, retry—answers one simple question: if the model only suggests, what safely turns a suggestion into real work?

First, know where this lesson is going

We are not trying to understand the entire Grok Build codebase yet. We are following one narrow path. Each step earns the next:

STEP 1 · NOWSeparate thinking from acting.
STEP 2Watch one calculator fix travel through the boundary.
STEP 3Open only the source-code boxes that the example needs.
STEP 4Give the advanced idea a familiar story.
The one story we will keep using

Maya has a tiny calculator program. It should say add(2, 2) = 4, but it says 8.

def add(a, b):
    return a * b       # the bug: multiply instead of add

Maya asks an excellent programmer for help. The programmer sits behind glass. They can read notes and write suggestions, but they cannot touch Maya's keyboard.

The programmer writes: “Change * to +.” That answer is correct. Yet the program is still broken, because a suggestion is not an action.

Pause: what must exist between the programmer and the computer?

A helper must carry information in both directions:

  1. Tell the programmer what Maya asked.
  2. Bring back requests such as “read this file.”
  3. Check whether each request is allowed.
  4. Use the keyboard, collect the real result, and take it back.

That helper is the beginning of a harness.

MODEL
The behind-glass programmer. It receives words and produces more words or a structured request. It can say “read the file”; saying it does not read the file.
HARNESS
The runner between the programmer and the computer. It prepares information, checks requests, performs allowed work, remembers what happened, and returns the observation.
TOOL
One specific ability the runner may use: read a file, change text, run a command, or search. A tool has a name and clear inputs.
RESULT
What reality returned: file contents, “permission denied,” a changed file, terminal output, or an exit code.

The model suggests the next step. The harness checks it, performs it, and brings back what actually happened.

The easiest test of understanding

Now—and only now—open the source-code words

The public Grok Build source uses names that sound mysterious when introduced without objects. We will translate each name into the calculator story before making any architectural claim.

1. What is Agent?

Here, Agent is not a robot, a process, or the entire application. It is a Rust struct: a named bundle of fields prepared for a coding helper.

Calculator example. Before asking the model anything, the program prepares a bundle:

Agent bundle
├─ system_prompt       “Inspect before editing. Test before claiming done.”
├─ tool_bridge         routes read_file, edit_file, run_command
├─ reminder_policy     nudge if a required check was skipped
└─ compaction_policy   summarize old conversation when space gets tight

“Agent holds X” simply means the Agent struct has a field containing X or pointing to X. It is the same as saying a school bag holds a notebook.

2. What is the system prompt?

It is the instruction text that tells the model how to behave in this role. “Rendered” means smaller pieces—base rules, workspace information, mode, and other context—have already been combined into the final string sent to the model.

Before rendering:
base rule     = “Inspect before editing.”
workspace     = “You are in /projects/calculator.”
finish rule   = “Run tests before claiming success.”

Rendered system prompt:
“Inspect before editing. You are in /projects/calculator.
 Run tests before claiming success.”

3. What is ToolBridge?

It is a switchboard between model-shaped requests and real tool implementations. The model sees a simple card saying read_file(path). When that request arrives, the bridge helps find the registered implementation and carries the result back in the expected format.

TOOL DESCRIPTION

What the model is told: the tool name, what it does, and which arguments it accepts.

TOOL CALL

The model's structured request: {"name":"read_file","path":"calculator.py"}.

IMPLEMENTATION

The actual Rust code that reads a file from the workspace.

TOOL RESULT

The returned observation: file text or a clear error such as “path denied.”

4. What kind of policies?

A policy is a small rule for a question that appears repeatedly. The exact configured values may change; the category of question stays stable.

PolicyQuestionSimple example
PermissionMay this action run?Reading calculator.py may be allowed; deleting many files may require Maya's approval.
CompactionIs the conversation becoming too large?Keep the bug, chosen fix, and test result; summarize old chatter.
ReminderIs an important check being forgotten?If the model tries to finish before testing, add a reminder to verify.

5. What is SessionActor, and what state does it have?

Think of one live chat as a small control room. The mostly prepared Agent bundle says how the helper is configured. SessionActor coordinates facts that keep changing while Maya's task runs.

CONVERSATION

The user messages, model outputs, tool calls, tool results, and current token count.

CURRENT TURN

Which prompt is running, whether it was cancelled, retry limits, timeouts, and maximum turns.

PENDING INPUT

A permission question or clarification waiting for Maya.

FILE STATE

Snapshots and rewind information needed to undo or recover changes.

NOTIFICATIONS

Text chunks, tool-started updates, results, and other events sent to the interface.

CONNECTED CAPABILITIES

The built Agent, permission handle, tool context, and MCP server state used by this session.

What the source proves

  • Agent fields include the rendered prompt, tool bridge, reminder policy, compaction policy, hosted tools, and configuration.
  • tool_definitions() gets tool descriptions through the bridge.
  • SessionActor has fields for live state, notifications, permissions, chat state, pending interactions, file tracking, timeouts, retries, MCP state, and the built Agent.
  • Workspace dispatch checks session and permission information before the underlying tool runs.

Limit: this describes the pinned public snapshot. It does not claim that private services contain only these parts.

The advanced phrase, rebuilt as a story

A restaurant before an “effect system”

A waiter may write “cook one soup” on a ticket. Writing the ticket does not cook soup. A cashier checks that the order is valid and paid. The kitchen performs the work. A receipt comes back saying what actually happened.

Now replace waiter with model, cashier with harness, kitchen with tool, and receipt with tool result.

Research edge: now translate the story into precise terms

The tool call is an effect request: structured data describing a desired interaction with the environment. The harness is the effect handler: it interprets that request, applies policy, invokes an implementation, and turns the outcome into an observation.

Complete mediation means every sensitive read or change must pass through that checking point. In the restaurant, nobody may walk into the kitchen and cook an unapproved ticket. In a coding agent, the model must not gain a hidden path to files, secrets, processes, or the network.

Partial observability means the model does not already know reality. It learns through returned observations. “File missing,” “permission denied,” and exit code 1 are not noise; they are the facts required for the next decision.

The question we ask

Who may suggest an action, who may perform it, which rule checks it, and what exact observation comes back?

Carry into the architecture

One protected doorway. The model never touches the computer directly. It sends structured suggestions to the harness. The harness checks and performs allowed actions, then returns reality as a result.

First boundary earned. We now know who can suggest and who can act. Next we watch the job itself before turning it into an agent loop.

0.2

Map the Human Workflow

A harness should not invent a mysterious robot ritual. First, watch what a careful human developer does from “something is wrong” to “here is the proof.” Then we can ask which parts software must support.

Why this comes immediately after the boundary

Section 0.1 gave us a protected doorway between suggestions and the computer. But a doorway does not tell us where to walk. Before building a loop, state machine, or planner, we need the ordinary work in the right order.

ALREADY EARNEDA model suggests; a harness safely acts.
STEP 1 · NOWWatch Maya solve the task by hand.
STEP 2Let a wrong guess and failed test teach us.
STEP 3Name the seven reusable verbs.
The common mistake

Maya sees add(2, 2) = 8. A beginner immediately opens the first file, changes the first suspicious symbol, and says “fixed.” A careful developer pauses.

Why? The screen shows a symptom, not yet a cause. Perhaps add multiplies. Perhaps the caller invokes it twice. Perhaps the test expects the wrong thing. Touching code before learning which story is true turns debugging into gambling.

Pause: what should Maya do before changing * to +?

She should collect enough facts to answer three small questions:

  1. Can I see the wrong result myself?
  2. Which code produced it?
  3. What is the smallest change that could make expected and actual match?

Only then does an edit become a testable plan instead of a guess.

The smallest useful workflow

OBSERVE
See the starting fact. Maya runs the example and records: expected 4, actual 8.
INSPECT
Look for facts that could explain it: the request, call sites, implementation, and relevant tests.
PLAN
Choose the smallest plausible change and say what result should follow if the idea is right.
EDIT
Make that exact change—no unrelated cleanup hidden inside it.
RUN
Ask the computer to execute the example, test, compiler, or checker.
COMPARE
Put expected beside actual. Passing and failing output both teach us something.
REPORT
State what changed and attach the observation that supports the claim.

Careful work is not “think, then type.” It is a chain where each observation reduces uncertainty and each action asks reality a question.

The source does not contain one magic function named solve_like_a_human(). It provides capabilities from which the workflow can be carried out: reading and searching for inspection, patching for editing, terminal execution for running checks, and session records for returning observations. Planning and comparing remain reasoning steps.

The pinned public source exposes the concrete capabilities needed by Maya's workflow:

  • read_file accepts a path and optional slice information, then returns observed file content.
  • grep accepts a pattern plus search scope and filters—the capability behind “check the call sites.”
  • apply_patch gives edits a structured, inspectable envelope rather than treating “change the code” as a vague instruction.
  • run_terminal_cmd executes commands and reports completion, failure, timeout, or background status.

What this does not prove: those tools alone guarantee careful behavior. The workflow order is a design model we derived. Prompts, policies, model decisions, and returned observations determine whether a particular turn follows it.

The research idea, rebuilt as a detective story

A detective's notebook

A detective writes two columns: what I saw and what I think it means. “The window is open” belongs in the first. “The visitor entered through it” belongs in the second. A fingerprint check may support that story or cross it out.

Debugging uses the same discipline. actual = 8 is an observation. “The caller runs twice” is a hypothesis. Search output tests it. A failing test is another observation—not an insult and not permission to hide the result.

Research edge: translate the notebook into precise terms

The developer maintains an epistemic state: the set of facts currently known, plus uncertainty that remains. Inspection is valuable when it reduces that uncertainty enough to choose a discriminating action.

A hypothesis should be falsifiable: it predicts an observation that could show it is wrong. “The caller invokes add twice” predicts two call sites; finding one rejects the hypothesis.

A test acts as an oracle only for the property it actually checks. A green unrelated test cannot prove addition works. A stale test can also encode the wrong expectation, so comparison still requires interpreting expected and actual.

This is a closed feedback process: act, measure the environment's response, compare it with the target, and adjust. Module 0.3 will earn the repeating loop from this observation; we do not install that architecture early.

The question we ask

What fact do I have, what do I merely suspect, and which smallest action would make the next decision less uncertain?

Carry into the architecture

Observe → inspect → plan → edit → run → compare → report. These are roles in careful work, not a promise that each happens exactly once. A failed comparison can send us back with one more fact.

Human workflow earned. We now have seven verbs and two retry examples. Next we compress their repeating structure without losing what each verb means.

0.3

Turn Work into a Loop

Module 0.2 looked like a line of seven verbs. But Maya's wrong guess and failed test both bent that line backward. We do not need seven boxes repeated forever; we need to discover the smaller pattern underneath them.

Why a checklist is not enough

The common problem

Imagine giving Maya a rule: “Inspect once, plan once, edit once, test once, then report.” It sounds organized. It also fails the moment reality disagrees.

Her first search disproved her guess. Her first test exposed a broken double(). In both cases the new result changed what she should think and do next. A fixed checklist cannot know the next action before the last observation exists.

Pause: which part actually repeats?

Not “edit, edit, edit,” and not the entire seven-step list. The repeating relationship is smaller:

  1. Receive a fact from the current world.
  2. Use that fact to choose the next move.
  3. Perform the move.
  4. Treat its result as the next fact.

Then ask whether there is enough evidence to stop. If not, repeat.

First regroup the seven human verbs

The words from Module 0.2 still matter, but they describe different levels. Observe, reason, and act are the repeating roles. The seven human verbs fit inside them:

“Inspect the code” hides three smaller events. Choosing which file to inspect is reasoning. Reading or searching it is an action. The returned text is an observation. One human verb may span several loop roles.

The easiest stop test

“I edited the file” is not enough. “I reached six iterations” is not enough. For Maya's task, stop only when all three are true: the requested example returns 4; the relevant tests pass; no observed failure remains unresolved.

A turn limit may stop runaway work for safety, but a forced stop is not proof of success. The report must say when work ended because of a limit rather than because the completion condition passed.

Only now open the production loop

Grok Build's public source uses more machinery than our three boxes, but its central turn flow preserves the shape we just derived: build the current request, ask the model for the next move, execute returned tool calls, add their results to conversation state, and sample again. A response with no tool calls reaches the completion path, subject to gates and limits.

Source proof / Grok Build snapshot a881e670
  • The turn loop starts a numbered loop iteration, builds the current request from conversation state, invokes the sampler, and may continue after compaction.
  • The model response is inspected for tool calls after response items have been recorded.
  • The no-tool branch runs turn-end checks and returns a completed outcome rather than unconditionally looping.
  • The tool branch executes requested tools, handles special outcomes, enforces a maximum-turn bound, and otherwise reaches the next loop iteration.

Source versus teaching model: the source proves a repeated sampling/tool-execution turn and concrete exit branches. Our “requested behavior + relevant checks + no unresolved failure” rule is the completion discipline earned from Maya's example. A model can still claim completion too early, so production adds reminders, gates, limits, and user-visible evidence.

What one full production trip teaches

The model never reads calculator.py. It proposes read_file. The bridge resolves the name, permission checks the effect, the workspace performs the read, and chat state records the returned text. Only then can the next model request contain that observation.

The final answer is also a branch: when the sampled response contains no tool calls, the session runs its end checks, finalizes bookkeeping, and reports completion. A maximum-turn stop follows a different path and must not be presented as proof of success.

The research idea, rebuilt as a thermostat story

A heater that looks again

A heater does not say, “I warmed the room once, so I am finished.” It reads the temperature, decides whether heat is needed, acts, and reads again. It stops heating when the measured temperature satisfies the target—not after an arbitrary number of clicks.

A coding agent is harder because its actions and measurements differ each time, but the principle survives: new measurements must be allowed to change the next action.

Research edge: translate the heater into precise terms

This is a closed-loop policy. The next action is chosen from the current observation and accumulated state, rather than from a complete action list fixed before execution.

The exit test behaves like a task-specific terminal predicate: a condition over current evidence that allows the process to finish. Because evidence can be incomplete or tests can be weak, the predicate is fallible; verification quality determines completion quality.

Safety asks whether every allowed iteration avoids unacceptable harm. Liveness asks whether useful work eventually reaches an exit instead of cycling forever. Permissions and sandboxes help safety; progress checks, cancellation, and iteration limits help liveness. A limit bounds cost but does not certify correctness.

A repeated state with no new evidence is a potential doom loop. The remedy is not merely “try again”; reasoning must choose a different information-gaining action, ask for help, or stop with an honest blocker.

The question we ask

What changed in our evidence, which next action follows from it, and what tested condition would let us stop honestly?

Carry into the architecture

Observe → reason → act → observe, repeated until a tested exit condition passes. Report and stop are the conditional exit; failure, uncertainty, or missing proof returns the new observation to reasoning.

Loop earned. We now know what repeats and when it may stop. The last Part 0 question is what exact object crosses each arrow without being confused for another.

0.4

Contracts Before Components

Boxes can be renamed. Libraries can be replaced. But if one side sends “read this file” and the other side cannot tell which result belongs to it, the loop is unsafe. Before adding more components, we must name the objects crossing the boundaries and the promises that keep them honest.

The familiar problem: two claim tickets

Why names alone are not enough

Maya gives a coat-check desk two jackets. Both are black. The clerk gives her tickets 17 and 18. Later, a jacket returns with ticket 17. Maya knows which request it answers even though the jackets look alike.

Now imagine the clerk says only “a jacket is ready.” If two requests are running, nobody can safely guess which one completed. A coding harness has the same problem when several reads, edits, or tests have similar names.

Pause: what must travel across the loop boundaries?

At minimum, four different kinds of object:

  1. The human's or runtime's words entering the conversation.
  2. A precise request to use one capability.
  3. The observed outcome tied back to that exact request.
  4. A notification for the interface saying what the runtime did.

If these are all treated as unlabelled text, errors become easy to hide and impossible to pair.

The smallest plain-language model

MESSAGE
One ordered contribution to the conversation. It says who spoke and carries content: Maya's goal, model text, or a runtime reminder.
TOOL CALL
A proposed action with a unique call ID, a tool name, and arguments. It is a request—not proof that the action ran.
TOOL RESULT
One terminal observation tied to a call ID. Success, error, denial, or cancellation must all return as distinguishable outcomes rather than disappearing.
EVENT
A runtime notification such as “tool call started” or “completed with error.” It helps a UI mirror reality. Seeing or emitting the event does not authorize the action.

The research idea, rebuilt as a ledger

Never erase a failed transaction

A careful shopkeeper does not tear a page out when a payment fails. They write “declined” beside that transaction number. Later, the balance can be explained because success and failure both left a record.

Tool failures work the same way. Missing data creates ambiguity: did the call never start, is it still running, or did it fail? A terminal error result closes the question without pretending success.

Research edge: translate the ledger into precise terms

The call/result exchange is a small protocol state machine: proposed → validated/allowed → running → exactly one terminal outcome. “Exactly one terminal result” does not claim the external effect can never run twice; retries and crashes require separate idempotency design. It says the conversation must not represent one call as both unresolved and completed twice.

The call ID is a correlation identifier. It preserves causal pairing even when calls look alike or finish out of order. An unknown ID is a protocol violation, not permission to attach the result to the nearest call.

Recording the result before resampling creates a happens-before relationship: the next decision is causally downstream of the observation. Sampling early would recreate the partial-observability bug from Module 0.1.

UI events are a projection of runtime facts. Projections may be delayed, dropped, replayed, or duplicated. Therefore authorization and conversation truth must live in runtime state, while the UI remains reconstructible from that state.

The question we ask

What kind of object is this, which exact attempt does it belong to, and what invariant prevents ambiguity or an unauthorized effect?

Carry into the architecture

Message · tool call · tool result · event. Validate and authorize before effects; pair each terminal result to one call ID; record it before resampling; preserve non-success outcomes; treat UI events as mirrors rather than authority.

The same worker can meet us in different places

A terminal screen, an automated build, and a code editor look unrelated. The design question is whether each needs a separate agent—or only a different doorway into one runtime.

2.1

One Engine, Many Front Doors

A front door decides how a person or program speaks to the agent. It should not secretly create a second permission system, tool loop, or definition of “done.”

The school kitchen problem

A school kitchen serves the same lunch in three ways. One child speaks to the counter worker. A teacher submits twenty lunch orders on a form. A delivery helper scans a machine-readable ticket.

Building three kitchens would copy recipes, allergy checks, and stock rules. Instead, each doorway translates its order into the kitchen's standard ticket. The kitchen cooks once; each doorway presents the result in the form its visitor understands.

Pause and decide: what should change when Maya moves from a terminal to her editor?
  1. The model, tools, permissions, and success rules.
  2. Only the way input enters and progress comes back.
  3. Everything, because an editor and terminal cannot share runtime state.

The smallest safe answer is 2. Keystrokes, command-line arguments, and JSON messages need different translators. Once translated, they should enter the same session and effect contracts.

Three words, in fifth-grade language

Front door
The place the request arrives: a full-screen terminal, an automation command, or a code editor.
Adapter
The translator at that door. It turns keys, flags, or protocol messages into the runtime's known requests, then translates updates back.
Engine / runtime
The shared worker behind the doors: session state, model loop, permission decisions, tools, results, and completion rules.

The door owns the conversation format. The engine owns what the agent is allowed to do and what counts as a truthful result.

The precise mechanism

  1. Receive in the door's native form. The TUI receives terminal events; headless mode receives a prompt and flags; an editor sends ACP requests over a transport such as stdio.
  2. Validate and normalize. The adapter decodes the request, checks its shape, and creates the corresponding session command without performing the coding task itself.
  3. Enter shared runtime contracts. A session records the prompt, samples the model, validates and authorizes tool calls, records paired results, and applies the same exit rules.
  4. Emit typed updates and an outcome. Progress, permission questions, tool lifecycle, text, errors, cancellation, and completion leave the runtime as explicit facts.
  5. Project back into the door's form. The TUI redraws panels, headless mode prints one plain or JSON result, and the ACP client receives protocol responses and session updates.

2.2

Composition Root

A production runtime should not discover half its dependencies while a prompt is already running. One startup path must choose the concrete parts, validate their agreement, construct them in dependency order, and publish only a complete runtime.

The robot-club assembly table

Leena's robot club has a motor, wheels, battery, remote control, safety switch, and instruction card. Every part works alone. The robot still fails if the battery voltage is wrong, the remote is paired to another robot, or the safety switch is attached after the motor starts.

The club appoints one assembly table. Before the robot moves, the table reads the instruction card, chooses matching parts, connects them in order, checks the safety switch, and hands over one ready robot. Children operating the remote never assemble batteries during a race.

Pause and decide: when should Grok discover that its model or tool configuration is invalid?
  1. After the model asks for the missing tool.
  2. While constructing the runtime, before any user prompt can run.
  3. Only when the UI tries to display the error.

The safe answer is 2. An invalid assembly is a startup/build failure, not a mysterious mid-turn behavior.

Doorway definition

Composition root
The small startup region that chooses concrete implementations, constructs them in dependency order, and returns the complete object the application will run.
Dependency
A real value another component needs: resolved configuration, an authentication manager, model catalog, client channel, filesystem, terminal backend, working directory, notification sender, or tool definition.
Construct
Call a named constructor with named inputs and receive a new object. Here, “assemble” never means “somehow connect things.”

The composition root does not solve the coding task. It creates the only runtime that is allowed to solve it.

The exact construction sequence

  1. The binary resolves launch intent. The selected mode, current directory, config files, managed settings, remote settings, and CLI overrides become an AgentConfig. This chooses facts such as model override, permission mode, plugins, endpoints, and client identity.
  2. The front-door spawn path constructs AuthManager. It receives the Grok home path and authentication configuration, then starts the appropriate refresh lifecycle. The same manager is later passed to model and runtime construction.
  3. bootstrap validates global prerequisites. It runs the managed-policy gate, resolves remaining config, validates model filters, initializes process-level services, and constructs ModelsManager from resolved config, prefetched entries, and auth.
  4. The client/runtime boundary is constructed. The pager path creates paired ACP client and agent channels, wraps the client sender in a gateway, and calls MvpAgent::with_models(gateway, config, auth, models).
  5. A session supplies workspace-specific facts. Its working directory, terminal backend, filesystem backend, state path, environment, notifications, session ID, capabilities, policies, and agent definition become an AgentRebuildSpec.
  6. AgentBuilder constructs the session's Agent. It resolves definitions and skills, selects and filters tool configs, rejects impossible curated toolsets, and passes a concrete SessionContext into ToolBridge::finalize_builder.
  7. Only the completed objects are published. The client receives an ACP channel; MvpAgent owns shared runtime state; the session owns an Agent whose prompt, policies, workspace resources, and tools agree. A prompt may now enter.

2.3

The Session Actor

A live coding session receives prompts, cancellations, model changes, monitor events, tool completions, and client queries that can arrive close together. If every caller edits the same fields directly, “what is running?” stops having one trustworthy answer.

The class register has one update desk

During attendance, one child says “present,” another corrects yesterday's total, and the teacher asks for the current count. If three people erase and rewrite the register at once, each change can be sensible while the final page is impossible.

The class uses one update desk. Requests wait on the desk. The desk takes one request, changes the register, records the result, then takes the next. Other people may do long jobs—such as checking another classroom—but only the desk decides when that result becomes part of this register.

Predict the safer design: who may change “current prompt” and “queued prompts”?
  1. Every UI, tool, and background task may mutate those fields directly.
  2. Callers send typed requests; one session loop applies state transitions.
  3. The model decides which write happened first.

The safe answer is 2. The model can suggest work, but runtime ordering must be enforced by executable data structures.

Four words without magic

Actor
A running task plus the session data it is responsible for and a loop that receives events. It is not a tiny person. Here the loop selects a ready command, completion, chat event, or notification event and runs that branch.
Mailbox
The receiving side of a channel where typed SessionCommand values wait. Grok Build's command channel is unbounded, so it provides ordering but not a built-in queue-size limit.
Handle
A cloneable proxy given to callers. Its cmd_tx sender can place commands in the mailbox. Shared prompt IDs and specialist handles provide limited observation; the handle is not a second SessionActor.
State
Named values whose current combination describes the session: running_task, pending_inputs, pending notifications, suppression and rewind flags, plus actor-retained configuration and resources. Conversation and token accounting are delegated through ChatStateHandle.

“The actor owns the session” means there is one authoritative command-processing locus—not that one giant struct stores every byte or performs every job.

The exact mechanism

  1. A caller holds SessionHandle. The handle is Clone + Send and contains cmd_tx, so a client adapter, leader, or extension can send a typed SessionCommand without borrowing the actor's fields.
  2. SessionCommand is the message protocol. Variants carry their complete inputs: Prompt includes a prompt ID, content blocks, mode, control flags, and one-shot reply channels; other variants cover cancellation, model/session changes, queue edits, notifications, and queries.
  3. run_session waits on several inboxes. A Tokio select! observes cmd_rx, turn completions, internal notification events, chat-state events, and other lifecycle signals. One chosen branch executes on the actor task before that task chooses again.
  4. A prompt becomes queued state. The Prompt branch calls queue_input. The state lock protects running_task and pending_inputs together, so the actor can decide whether to queue, interrupt, or start work from one view.
  5. The long turn is delegated. maybe_start_running_task starts model/tool work and arranges for a result on completion_rx. The actor loop can therefore continue accepting cancellation and other commands while the turn performs slow inference or tools.
  6. Completion re-enters through a channel. The completion branch flushes replay-buffered output, calls handle_completion, performs turn-end bookkeeping, drains safe notifications, and may start the next queued input.
  7. Notifications have a separate transport object. NotificationSender contains the client gateway, a gateway-enabled gate, and persistence sender. Internal SessionEvent values pass through event_tx so buffering and delivery order remain explicit.

Research edge: actor serialization, linearization points, and backpressure

The actor model replaces shared direct mutation with messages and isolated transition logic. For a session command, the useful linearization point is not when a caller presses a button or sends on cmd_tx; it is when the actor branch admits and applies the command to authoritative state. Before that point the request is only in transit.

This gives a serial history of state transitions even though inference, tools, persistence, and UI delivery are concurrent. It does not make the whole system single-threaded: long work is delegated, then its completion is reintroduced as another event. Reentrancy remains dangerous if a handler waits for an answer that can only be produced by the same blocked actor, which is why one-shot responses and spawned tasks need deliberate boundaries.

Grok Build's cmd_tx is an unbounded channel. That avoids a sender waiting merely to enqueue a command, but it is not backpressure. A producer faster than the actor can grow memory and latency. The design therefore needs admission rules, queue inspection/editing, cancellation, coalescing or caps for high-rate event streams, and telemetry for queue depth.

Serialization also needs terminal-event discipline. A prompt must not become both cancelled and completed merely because two producers raced. The actor's transition code, prompt IDs, queue invariants, and completion kinds together define which terminal fact is accepted and what work may start next.

An authoritative state transition answers “what is true now?” Other parts of the product still need to learn what happened. If they discover it by reading private fields or receiving secret callbacks, reload, replay, debugging, and multiple clients disagree.

Plain definitions

Command
A typed request to try something, such as Prompt, Cancel, or “flush now.” It may be rejected or produce a different outcome than requested.
State transition
The authoritative code changing session truth—for example, moving prompt q31 from waiting to running_task. This is the decision, not the announcement.
Event or notification
An immutable message describing an observable fact after or during work. Grok Build stamps updates with fields such as eventId, promptId, timestamp, update type, and optional chunk identity.
Consumer

Replay

Transient event
A live-only hint that should disappear after reload because durable state can reconstruct the truth. Cosmetic plan cleanup is one source example.

Command asks. Transition decides. Event reports. Conflating those three turns a rejected request or a temporary UI change into false history.

The exact event path

  1. A typed command enters the session actor. The actor validates and applies its own transition. A Prompt command can become queued/running state; a malformed or removed prompt does not become a success event merely because someone requested it.
  2. The producer constructs a protocol update. send_update_full obtains token and timing context, generates an event ID and timestamp, attaches the current prompt ID and optional chunk ID, then wraps the update in an ACP SessionNotification.
  3. High-frequency updates enter event_tx. SessionEvent::Notification carries ACP or xAI notification shapes into the actor loop. SessionEvent::FlushReplay is a separate barrier request with an optional acknowledgement.
  4. The actor-owned ReplayBuffer merges and debounces. The event branch calls consume_chunk. Compatible streaming chunks may wait and merge; incompatible or boundary events make one or two buffered notifications ready for emission.
  5. One dispatch point applies durability rules. Buffered ACP text/thought updates flow to emit_notification_direct, which logs identity, sends a persistence message unless excluded, and forwards to the gateway only when that session's gate is enabled.
  6. Not every live update is durable. xAI ToolCallDeltaChunk values are gateway-only because the assembled canonical ACP ToolCall is persisted later. emit_transient_notification is also live-only by contract.
  7. Completion forces ordering boundaries. Before handling turn completion, the run loop flushes the replay buffer. flush_to_disk can request an actor flush, then send PersistenceMsg::FlushAndAck and await confirmation from the persistence actor.
  8. Persistence has its own merge and append loop. Consecutive ACP text chunks may merge before writing; xAI one-shot updates write directly. A stored durable update can later be loaded or replayed without executing the original command again.

2.5

Streaming and Cancellation

A production agent should show useful progress before a long model response finishes, yet it must also stop honestly. Hiding the spinner is not cancellation. The runtime must coordinate streams, tools, queues, subprocesses, timeouts, and one unambiguous terminal outcome.

The school tap and the stop valve

Meera fills a bucket from a long pipe. Water arrives as many small splashes, so she can see progress before the bucket is full. If she closes the valve, the request to stop travels through the pipe. A little water already inside may still drain out; water already in the bucket does not jump back into the tap.

A truthful system distinguishes three moments: Meera asks to stop, the valve closes production, and the pipe finishes draining or safely discarding what was already on its way. Only then can the bucket be labelled “stopped.”

Prediction: when may the UI show “cancelled”?
  1. Immediately when the stop button is pressed, even if tools keep running.
  2. After the cancellation request reaches the owner, owned work is torn down or fenced off, state is repaired, and one cancelled terminal outcome is published.
  3. Only when the model voluntarily writes the word “cancelled.”

The safe answer is 2. Pressing stop is intent. A terminal cancellation is an accepted runtime fact.

Plain definitions

Stream and chunk
A stream is a sequence that arrives over time. A chunk is one piece: text delta, reasoning delta, tool update, metadata, or terminal event. A chunk can be useful before the whole response exists.
Cancellation request
A typed message asking an owner to stop work identified by session, prompt, or sampler request ID. Sending it does not prove the work has stopped.
Accepted terminal outcome
The single final meaning recorded after teardown: completed, failed, or cancelled. Later bytes must not change that terminal meaning or revive the old turn.
Cancellation token
A shared cooperative signal. One owner fires it; code at a cancellation-aware wait or check observes it and exits. It does not interrupt arbitrary machine instructions instantly.
Idle timeout
A deadline for a stream that makes no useful progress. Grok Build checks both total transport silence and streams that send empty keepalives without meaningful content.
Safe boundary
A place where stopping cannot leave a half-written protocol or contradictory state: between chunks, before the next retry, around a tool process handle, at queue transition, or before publishing the terminal event.
Backpressure
A rule that prevents producers from outrunning consumers forever. Buffering and merging reduce pressure; bounded queues, flow control, admission, or dropping explicitly transient detail may still be required.

Cancellation is cooperative control flow plus terminal-event discipline—not a universal undo button.

The exact streaming and cancellation lifecycle

  1. The session submits one identified sampler request. SamplerActor creates a CancellationToken, stores it under the request ID, clones it into a spawned per-request task, and lets live SamplingEvent values flow through the shared event channel.
  2. A backend adapter turns transport events into Layer-2 events. Text, thought, tool, metadata, retry, and backend-tool progress can arrive incrementally. The transforms promise a terminal Completed or Failed on their ordinary success/error paths.
  3. Two idle clocks protect liveness. A timeout around stream.next() catches no transport chunks. A separate meaningful-content clock catches empty or keepalive traffic that would otherwise keep the connection alive forever without progress.
  4. drive_l2 races cancellation against the next item. Its biased select! checks the cancellation token before consuming another ready stream item. Non-terminal events are forwarded; a terminal event becomes a completed/failed attempt.
  5. The session publishes chunks through the event/replay path. Chunks can be merged and displayed, but the prompt remains running. Backpressure is not solved merely because the UI can see deltas; unbounded producers still need admission and merge/drop policy.
  6. A user stop becomes SessionCommand::Cancel. The actor loop first flushes the replay buffer so already-visible output has a durable boundary, then calls cancel_running_task with explicit child/background/rewind choices and the trigger.
  7. The session tears down work in ownership order. It gates task wakes, kills owned foreground terminal processes, optionally cancels subagents/background tasks for hard teardown, removes the running queue front while preserving eligible queued prompts, then aborts the running task handle.
  8. Sampler cancellation is cooperative. A SamplerCommand::Cancel removes the active request and fires its token. The request task observes the token at its loop or stream-select boundary, emits a non-retryable cancellation failure to sampler consumers, and completes its one-shot with an error.
  9. The session publishes one cancelled turn terminal. It records a cancelled turn-end category, clears the prompt resource and active flags, stamps the cancel trigger, and emits TurnCompleted with StopReason::Cancelled. Only then may a preserved next prompt be promoted.
  10. Late output is fenced by identity and ownership. A process kill or future abort may race with already-produced bytes or a task finishing. Those bytes may be drained, ignored, or recorded only within the old prompt boundary; they must never mutate a new turn or replace its terminal meaning.

Research edge: cancellation safety is a property of every await boundary

Cooperative cancellation works when tasks periodically wait or check a token and clean up on exit. A CPU loop that never yields, a remote server already processing a request, or a child process without an owned handle may continue temporarily. Cancellation latency is therefore measurable architecture, not a button animation.

Structured concurrency asks every child task to live inside a parent scope with a handle, deadline, and terminal join policy. Interactive cancel may preserve background work; hard teardown may kill it.

Flush-before-abort, RAII guards, prompt IDs, queue-front invariants, kill-before-task-abort, and one terminal event are concrete safety mechanisms.

Idle timeout is a liveness failure, not user cancellation. It should produce a failed terminal with enough detail to distinguish “no chunks” from “keepalives but no meaning.” Retrying may be valid under policy; user cancellation is marked non-retryable so the system does not restart work the user stopped.

Streaming creates backpressure across network, parser, event channel, replay buffer, persistence, and UI. Merge/debounce protects consumers from tiny chunks, but unbounded channels can still grow. Plain definitions

An edit is a claim about the file that was observed. If the file has changed, blindly applying old coordinates can silently corrupt new work.

Prediction: what should happen when an edit anchor is stale?
  1. Guess the nearest line and write anyway.
  2. Reject with current context, then re-read and recompute.
  3. Overwrite the entire file.

Answer 2. A stale precondition is useful evidence, not an inconvenience to bypass.

Plain definitions

Precondition
A fact that must still be true at commit time: exact old text, a line anchor hash, non-overlapping ranges, or expected file state.

The file content against which all edits in one batch are validated.

Check every operation and overlap before applying any member of the batch.

Running a command is not one function call. It creates a process with identity, pipes or a terminal surface, streamed bytes, deadlines, ownership, exit state, and sometimes a background life.

Class-five doorway · the science-fair motor

Leo switches on a motor. He writes its label, watches the wire, catches measurements, and knows where the off switch is. Walking away does not stop it. Moving it to another table does not make it survive the school closing.

Prediction: when a foreground command exceeds its short wait budget, what are the honest choices?
  1. Pretend it completed.
  2. Kill it with a timeout, or explicitly background it and return a task handle.
  3. Forget its process ID.

Answer 2. “Still running” is a lifecycle state, not an error message.

Plain definitions

Process
An operating-system execution. The local backend can track a PID or process group, but exact identity and kill guarantees are backend-specific and sometimes best-effort.
Pipe
A byte stream connected to stdout or stderr. Grok Build's local backend uses piped streams for command capture.
PTY
A pseudo-terminal that makes programs behave as if attached to an interactive screen. PTY behavior and piped capture are not interchangeable; the pager has PTY testing while command backends use their own contracts.
Foreground
The turn waits for completion, timeout, cancellation, or an enabled automatic-background transition.
Background task
A tracked process that returns a task ID immediately and is later queried, awaited, or killed. Runtime tracking does not imply survival across host restart.
Ownership
The actor and tool call correlate local work. An owner_session_id may also be present, but is optional rather than a universal process field.
Exit fact
Exit code, signal, timeout, or still-running/backgrounded state. Output alone cannot prove success.

A command is complete only when its owned process lifecycle says so.

Smallest mechanism · spawn → identify → stream → decide → drain → terminalize

  3. Read stdout/stderr incrementally and correlate chunks with the call.
  4. On completion, drain remaining bytes and record exit status.
  5. An ordinary timeout kills/fails the foreground run. Automatic transition requires both enabled_background and auto_background_on_timeout; an explicit is_background=true starts in the background.
  6. For background work, preserve a task handle for get/wait/kill until terminal state.

A correct tool can return more data than the model, UI, or transport can safely carry. The harness must preserve useful evidence without pretending a preview is the whole result.

Class-five doorway · the giant telescope photo

A telescope makes a 2 GB photo. The teacher puts a small preview in the notebook and stores the original in a labelled cabinet. For a long book, she gives page 1 and tells students how to ask for page 2. She never cuts the photo and claims it is complete.

Prediction: what must a truncated result contain?
  1. Only the first bytes.
  2. A useful preview, explicit truncation/completeness metadata, and a recovery route when full data is retained.
  3. The word “large.”

Answer 2. Loss must be visible, and recovery must be truthful.

Plain definitions

Inline budget
The amount allowed directly into model-visible output.
Truncation
Discarding some inline content and marking that loss.
Paging
Returning one addressed window—such as read_file's 1-based starting line plus line limit, or a document page range—with a way to request another. Windows are not stable across file mutation unless identity is checked again.
Attachment/pointer
A separate retained payload or output file referenced by metadata. A pointer is useful only if the next tool can actually read it.
Soft wrap
Adding line breaks without losing bytes; different from truncation.
Tool-specific policy
Grep, read, bash/task output, MCP, and images use different limits and recovery forms. There is no proven universal summarizer, pager, retention rule, or cap.
